Socket đang nói gì

Bấm Kết nối để bắt đầu. Mỗi dòng là một frame thật trên socket.

Robot và server nói chuyện với nhau thế nào

Một lượt hội thoại

  1. Thiết bị mở WebSocket tới /xiaozhi/v1/, kèm header Authorization, Protocol-Version, Device-Id, Client-Id. Trình duyệt không đặt được header nên trang này dùng query param — server chấp nhận cả hai.
  2. Thiết bị gửi hello rồi chờ tối đa 10 giây. Nếu không có hello trả về, nó coi như kết nối hỏng.
  3. Server trả hello kèm session_id và audio_params. Đây là lúc thiết bị biết phải giải mã ở sample rate nào.
  4. Thiết bị gửi listen start rồi stream Opus nhị phân liên tục. Ở mode auto nó không bao giờ gửi listen stop — server tự quyết định câu đã kết thúc bằng VAD.
  5. Server gửi stt (chữ để hiện lên màn hình) rồi tts start.
  6. Server gửi audio Opus theo nhịp, kèm tts sentence_start cho phụ đề.
  7. Server gửi tts stop. Ở mode auto thiết bị quay lại listening và tự gửi listen start mới cho lượt sau.

Hai ràng buộc dễ làm hỏng audio

Thiết bị chỉ nhận audio khi đang ở state speaking. Gửi trước tts start thì gói bị vứt, không có lỗi nào báo về. Vì vậy thứ tự luôn là stt → tts start → audio.

Hàng đợi giải mã chỉ chứa 20 gói. Đầy là drop im lặng. Nên server phải phát audio theo đúng nhịp thời gian thực chứ không được đẩy hết một lúc — nhìn cột Nhịp trung bình để kiểm chứng.

MCP: robot là server, backend là client

Ngược với trực giác. Thiết bị khai features.mcp, backend hỏi initialize rồi tools/list, và khi LLM muốn điều khiển phần cứng thì backend gọi tools/call xuống thiết bị. Tất cả nằm trong {"type":"mcp","payload":…} — dùng chung socket với audio nhưng là hai việc tách biệt.

Trang này đóng luôn vai MCP server, nên bạn sẽ thấy đủ cả ba bước ở cột bên phải. Tool có đánh dấu user-only bị giấu khỏi LLM có chủ đích.
